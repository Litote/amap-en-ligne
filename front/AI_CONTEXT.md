# AI Context — Front (Flutter)

> Front-specific context for AI agents. System-wide contract, wire format, and cross-component invariants: [`../AI_CONTEXT.md`](../AI_CONTEXT.md).

---

## Role

Offline-first Flutter client (Android, iOS, Web from one codebase). All authenticated traffic goes through the back's single endpoint `POST /v1/sync`: scope-keyed cursors + pending mutations out, authoritative `authorized_scopes` + one `ScopeSyncResult` per scope + per-mutation outcomes in.

> **Contract note (2026-06):** `Owner` and `Member` do not carry a `sub` field on the wire — front mappings use `owner_id` / `member_id` as entity identifiers. The JWT `sub` is auth-scoped metadata only (e.g. private feed keys `member:{sub}` / `owner:{sub}`).
>
> **Member status**: `Member.account_status` is the single source of truth for a member's lifecycle (non-nullable, `@Default(MemberAccountStatus.active)`; omitted on the wire means ACTIVE). `user_settings` (Map) and `user_preferences` (typed) are carried as-is.

## Layered architecture (`lib/`)

```
domain/        pure Dart, zero Flutter/IO — models, sync types, auth/server contracts
data/          adapters (drift, dio, repositories, auth, push) — depends on domain/ only
presentation/  BLoC + go_router + Material 3 screens — depends on domain/ only
```

`presentation` never imports `data` directly: repositories arrive via `RepositoryProvider`, blocs via `BlocProvider`.

- **`domain/model/`** — one Freezed model per synced entity, snake_case via `@JsonKey`. `organization_member_view.dart` holds pure selector functions (volunteer dashboard, history, coordinator displays).
- **`domain/sync/`** — `EntityType` enum + wire-name map, `EntityPayload` (sealed), `ClientMutation` (`tmpIdPrefix = 'tmp_'`), `MutationOutcome`/`MutationErrorCode`, `SyncRequest`/`SyncResponse`, `ScopeSyncResult`, scope-key helpers in `sync_scope.dart` (incl. `memberScopeKey(sub)` / `ownerScopeKey(sub)`).
- **`data/local/database.dart`** — drift schema: one table per synced entity (tables in the `database/tables.dart` part; `AppDatabase` CRUD split into private per-domain mixins in `database/*_queries.dart` parts — mixins, not extensions, so `Mock implements AppDatabase` keeps stubbing them), `sync_cursors` keyed by **scope key**, `pending_mutations` (with non-nullable local-only `scope_key` for pruning/remap). Most entity tables store full JSON blobs.
- **`data/network/`** — `buildSyncDio` (auth interceptor, signOut on 401) / `buildPublicDio`; `SyncApi` (POST /v1/sync); `PublicApi` (public bootstrap endpoints + `describeActivation` (GET preview) / `activate`, typed conflict exceptions; `ActivationError.weakPassword` maps the back `400 WEAK_PASSWORD`); `AdminApi` (only `searchProducers` — the one authenticated REST call).
- **`data/auth/`** — `GoTrueAuthService` (direct REST via dio) and `CognitoAuthService` (`amazon_cognito_identity_dart_2` behind a `CognitoSessionGateway`; `USER_PASSWORD_AUTH`, access token only — never the idToken) behind one `AuthService` interface; `AuthTokenStorage` (mobile: `flutter_secure_storage` — Keychain on iOS, AES-GCM cipher storage on Android (v11 dropped the EncryptedSharedPreferences backend); web: sessionStorage for temporary sessions / localStorage for durable ones with "remember me"); `JwtClaims` (unsigned payload decoder — back is the trust boundary); `RememberedUserContextStorage` (email/server prefill, separate from the session).
- **`data/server/`** — `ServerCatalog` backed by static `server_presets.dart` (temporary bootstrap), `ServerConfigStorage` (persisted selected config), `ServerDiscoveryDocument` + `DiscoveryDocumentServerCatalog` (federation-ready).
- **`data/repositories/`** — one repository per entity, mirroring `ProductTypeRepository`: optimistic local write + `ClientMutation` enqueue (some flows are deliberately non-optimistic and wait for the sync outcome, e.g. join-request review, owner/producer lifecycle).
- **`data/sync/sync_repository.dart`** — the orchestrator (see below).
- **`data/push/`** — `PushRegistrationService` + `PushTokenSource` (`FcmPushTokenSource` wraps `firebase_messaging`, degrades gracefully without Firebase config).
- **`presentation/`** — screens follow the UI specs under `documentation/feature/fr/ui/` (the spec is the contract — see `front/AGENTS.md`). Routing in `presentation/router.dart` (go_router, auth-guarded redirects, `/login?from=...` intent preservation, role guard `_roleGuardRedirect` mirroring the menu — a screen of another role sends back to the landing page). Sub-screens are opened with `context.go` (real URL) — **never `context.push`**: on web go_router does not reflect an imperative push in the browser URL (the screen is lost on reload, and `GoRouter.optionURLReflectsImperativeAPIs` is discouraged upstream); there is no `context.push(` left in `lib/`. A sub-screen route must rebuild everything from its path (an `extra` is only a shortcut): see `DeliveryTemplateRouteScreen` (`/admin/delivery-templates/:id`, never an empty creation form under an edit URL) and `DeliveryDescriptionRouteScreen` (`/coordinator/deliveries/:id/description`, org read back from the cache). They leave with `popOrGo` (`presentation/nav/back_navigation.dart`) or `backToDeliveryList` / `backToDeliveryTracking`; a route that needs an object handed over by `extra` must also rebuild it from its path id (e.g. `ItemTypesRouteScreen`).
- **`presentation/delivery/`** — shared delivery-display building blocks (reuse instead of re-duplicating): `DeliveryCard` (one card for the member planning + dashboard, `DeliveryCardVariant.planning`/`dashboard`), `delivery_format.dart` (date/time formatters), `delivery_status_chip.dart` (`DeliveryStatusChip`/`SlotStatusChip`), `delivery_coordinators.dart` (`CompactCoordinatorsLine`/`CoordinatorsSection`), `delivery_registration_actions.dart` (`RegisterButton`/`UnregisterButton` + actions). The pure slot/registration selectors live in `domain/model/organization_member_view.dart`. **`deliveryVolunteerStaffing(delivery, {mainContractIds})` is the single source of truth for the "N/M bénévoles" counter** — sum of (`currentRegistrations`, `requiredVolunteers`) over all non-cancelled STANDARD **and** EARLY slots; every display site routes through it (`DeliveryCard`, `volunteer_dashboard_section`, `deliveryVolunteerSummary`, the coordinator tracking progress bar). **Only main contracts count** (`Contract.isMainContract`): callers pass `mainContractIds` (derived via `mainContractIdsOf(contracts)`) so secondary contracts (eggs, fruit…) contribute no volunteer need — fallback counts every contract when none of the delivery's links is main (legacy data). The coordinator summary `deliveryVolunteerSummary` falls back to `Delivery.minVolunteersRequired` only when the delivery links a main contract (or the org has none): a delivery carrying only secondary contracts shows « Aucun bénévole requis » (`volunteerSummaryLabel`) and no status chip. **Coordinators never count**: the delivery-wide coordinator union (`deliveryCoordinatorIds`, every linked `DeliveryContract.coordinators`) is excluded from `current` via `activeRegistrationsExcluding`, even when a coordinator of one contract registers on another contract's slot. `deliverySlotStatus` and the coordinator tracking "Bénévoles présents" count apply the same main-filter + coordinator-union rules. The coordinator list chip `deliverySlotStatus(..., now:)` applies the same window: < 50 % is « Critique » only within `kUrgentNeedWindow`, « Ouvert » before. Collection progress (tracking « Contrats collectés », finalisation summary/PDF) counts only `deliveryContractsToCollect` — links with at least one basket. The member-facing urgency badge (planning + dashboard `DeliveryCard`) comes from `volunteerNeedLevel` (`domain/model/volunteer_need.dart`): < 50 % staffed is « 🔴 Besoin urgent » only within `kUrgentNeedWindow` (3 days, the back `SHORTAGE_LEAD`), « 🙋 Bénévoles recherchés » before; 50–80 % « Places limitées ». Volunteer slots are materialised on the **main contract link only** (`defaultVolunteerSlots` is attached to the main link by the delivery form and weekly generation; **no slot is created when no linked contract is main** — the delivery form also hides the volunteer minimum field + slot-time block in that case, lists only main-contract slots, and prunes legacy empty volunteer slots off non-main contracts on save). `registerToSlotAction` likewise targets a **main contract's** slot (`mainContractIds` passed from the cards via `RegisterButton`), so a volunteer never lands on a secondary contract; legacy fallback to every contract only when none is flagged main. Slot capacity reads `slot.requiredVolunteers` for both kinds (`slotCapacity`); the EARLY slot is materialised with `requiredVolunteers` = the resolved early capacity (delivery override, then `DeliveryTemplate.earlySlot.maxVolunteers`), so the slot row is the override-aware source and no template lookup is needed at read time. A `Delivery` also carries optional `standardEndTime` / `volunteerArrivalTime` / `earlySlot` overrides of the template's slot times (resolution: delivery override → template → hard-coded default), materialised by `defaultVolunteerSlots` in `domain/model/delivery_slots.dart`; the coordinator delivery form authors them (`_SlotTimesBlock`, "Horaires des créneaux").

## Sync machinery

- **`SyncRepository` applies the whole response in one drift transaction**: treats `authorized_scopes` as authoritative discovery (evicts disappeared scopes + their pending mutations), applies bootstrap as a full authoritative resync even after an incremental request, remaps `tmp_*` ids, rewrites still-pending mutations referencing them, drains acknowledged mutations. REJECTED outcomes surface via `SyncSuccess.rejectedMutations`, and the scopes of definitively refused mutations are **re-bootstrapped in the same `sync()` call** (cursor reset inside the transaction, then one extra round-trip) so the refused optimistic write disappears from the cache. Exception: a REJECTED outcome with `MutationErrorCode.internalError` (transient server-side failure) is **not** drained — the mutation stays queued and is resent on the next sync (offline-like semantics).
- **Handler registry** — `data/sync/entity_sync_handler.dart` (interface + `buildEntitySyncHandlers()`, re-exports `data/sync/handlers/*`): one `EntitySyncHandler` per `EntityType`, one file per handler, owning snapshot eviction, upsert, delete, and `tmp_*` remap. The registry asserts full coverage at construction — **adding an `EntityType` without a handler crashes at startup**.
- **`tmp_*` remap** — when `MutationOutcome.serverEntityId != tmpId`, the row's primary key is rewritten (delete + insert in-transaction). **Remap helpers (`db.remap*Id`, handler `remapTmpId`) must never call `transaction()`**: they already run inside the sync transaction, and on web with cross-origin isolation (COOP/COEP → drift OPFS-locks storage, drift ≥ 2.35) a nested transaction never commits — the whole sync hangs (pinned by `test/data/sync/sync_nested_transaction_test.dart`). No-account producer remap also rewrites embedded `Organization.producers[]` references (not `Organization.products[]`). Contract remap (`ContractSyncHandler`) also rewrites `Organization.deliveries[].contracts[].contractId` in pending `OrganizationPayload` mutations AND in the cached `organizations` table (via `db.remapContractId`). `BasketExchange` nested requests: `serverEntityId` carries the aggregate root id — the allocated `requestId` is recovered by diffing `requests` after the next sync.
- **Sync triggers** — app start, manual refresh, post-mutation flush (`SyncEvent.mutationApplied()` dispatched by screens), `connectivity_plus` reconnection (none→online transitions only). No periodic polling.
- **Offline failures are classified, not generic** — `SyncRepository` maps transport-level `DioException`s (connection error/timeouts, `unknown` wrapping a SocketException) to `SyncOutcome.networkFailure()` → `SyncState.offline()`; HTTP error responses stay `SyncOutcome.failure`. UI: `SyncStatusBanner` shows a reassuring "Serveur injoignable…" banner (retry only, no report), and `SyncOfflineListener` (mounted above the `MaterialApp` in the authenticated shell, snackbar via `scaffoldMessengerKey`) surfaces the same message on any screen. Shared copy in `presentation/sync/sync_messages.dart`.
- **Tenant resolution** — no tenant claim in tokens: the tenant is resolved from the persisted sync cursors — `AuthBloc.state.producerAccountId` from the `producer-account:*` cursor for producers (may differ from the `sub`; before the first sync the `sub` is used as fallback), `organizationId` from the `organization:*` cursor for AMAP members. Repositories resolve the `organizationId` lazily: exact match first, then the org id derived from the `organization:*` sync cursor — so non-producer users see empty data until the first sync completes.

## Key decisions

- **Freezed + json_serializable** with global `include_if_null: false` (matches back `explicitNulls = false`); snake_case via explicit `@JsonKey(name: ...)`. Wire compatibility pinned by `test/domain/sync_wire_format_test.dart`.
- **Hand-rolled sealed parents for `EntityPayload` / `MutationOp`** — Freezed 3.x drops the `type` discriminator for single-variant unions, so the parents are manual `sealed class`es with explicit `fromJson` switch / discriminator-injecting `toJson`; variants stay Freezed.
- **drift** for the local cache: type-safe SQL, first-class transactions (needed for remap + atomic snapshot apply), cross-platform via `drift_flutter`. Web assets shipped manually: `web/sqlite3.wasm` + `web/drift_worker.dart.js` — downloaded from the GitHub release matching the `drift` version in `pubspec.lock` (`gh release download drift-<ver> --repo simolus3/drift -p sqlite3.wasm -p drift_worker.js`, the latter renamed); refresh them on every drift upgrade. **Corruption self-heal (web)**: `database_open_web.dart` opens a throwaway probe connection (`enableMigrations: false`) and runs `PRAGMA quick_check` via `isDatabaseHealthy` (`database_integrity.dart`); on a malformed image (e.g. a Firefox multi-tab write race on the `unsafeIndexedDb` storage) it reports a groupable Sentry event (`'Local cache corrupt — recreated'`, warning, with `local_cache` context) for tracing, then `deleteDatabase`s the stored copies and recreates an empty cache — safe because the cache is server-authoritative and the next sync rebuilds it. Recovery happens on (re)load. **Schema version mismatch**: `AppDatabase.migration.onUpgrade` drops every table listed in `sqlite_master` (including obsolete ones) and runs `createAll()` whenever the stored `user_version` differs from `schemaVersion` (up or down, e.g. a pre-squash database) — no step-by-step migrations (exceptions, both keeping the queue: v3/v4→v5 creates `cache_owners` if missing and deletes the `organization:*` cursors, so caches synced before the back masked the other members' contact details re-bootstrap those scopes); the next sync rebuilds the cache and unsynced `PendingMutations` are lost. The open/recover **control flow** is extracted into the platform-agnostic `openDatabaseWithRecovery` (`database_recovery.dart`, unit-tested) so the wasm/Sentry specifics stay in the web file.
- **French dates** — any date showing the day of month goes through `frenchDateFormat(pattern)` (`presentation/common/french_date_formatting.dart`), not `DateFormat(pattern, 'fr')`: it writes « 1er » on the first (« jeudi 1er octobre »). Form messages reuse the shared constants of `domain/validation/input_rules.dart` (`kFieldRequiredMessage` « Ce champ est requis. », `kPositiveCountMessage`, `kInvalidEmailMessage`, `kInvalidUrlMessage`) rather than local variants.
- **Tenant-scoped routes** — every shell route that depends on the tenant is built through `tenantScoped((tenantId) => Screen(...))` (`presentation/router.dart`): a `BlocSelector` on `AuthBloc` (selector `tenantOf`: a producer's resolved `producerAccountId`, else the member's `organizationId`, else the `sub`) that keys the screen by tenant. It must listen to `AuthBloc` itself — go_router does **not** re-run an on-screen page's builder when the auth state changes. After a page reload the tenant is the `sub` until `AuthBloc` resolves the real one from the cache; the key change remounts the screen so its blocs stop reading/writing under the `sub`. `AuthBloc` resets the resolved tenant when another user signs in on the same tab (a token refresh keeps it). New tenant-dependent routes must use it.
- **Auth session semantics** — lazy single-flight refresh within 30s of expiry; refresh failure ⇒ `Unauthenticated` + storage cleared; back 401 ⇒ `signOut()`. `SyncBloc` is provided keyed by `producerAccountId`, so login/logout recreates it cleanly. **The local cache belongs to one user**: `cache_owners` stores the auth `sub` the cache was synced for, and `SyncRepository` (`currentUserId`) wipes the whole cache (`clearAll`, pending mutations included) before syncing as a different user — a session that replaces another without a logout (account activated in a new browser tab sharing the same IndexedDB copy) must never resend the previous user's mutations under its own token (seen as a `FORBIDDEN missing owner role` replay of an OWNER approval). That key swaps the **whole `MaterialApp`**, so the keyed subtree is wrapped in `InactiveSubtreeFocusGuard` (`presentation/common/inactive_subtree_focus_guard.dart`): on web the engine moves DOM focus mid-frame (semantics route focus) and the resulting view focus traversal would otherwise sort the replaced app's still-registered focus nodes, whose render objects are detached (`Null check operator` in `getTransformTo`); the guard's scope stops accepting focus on `deactivate()`. Keep it if the shell is restructured.
- **App boots on the public home** (`/`); authenticated users are redirected to `/product-types`. Server selection is a secondary screen reachable from login; switching server clears auth + config.
- **Push registration is server-authoritative** — `PushRegistrationService` registers `DeviceToken`s only on the private feeds present in persisted sync cursors (never guessed from claims), idempotent by token, bound to FCM token rotation, fired on every `SyncSucceeded`. `firebase_options.dart` ships placeholders (build/boot only — real delivery needs a real Firebase project). `unregisterCurrentDevice` exists but is not auto-fired on logout (deferred).
- **`BasketExchange` is a reciprocal swap** — `BasketExchangeRequest` carries `proposedDeliveryId` / `proposedContractId` (the requester's counter-basket, required at submit; `SubmitRequestDialog` picks it from the requester's eligible deliveries). The offerer **validates** one request (`acceptRequest`) or **refuses it individually** (`refuseRequest`, offer stays OPEN — now supported by the back). Pure selectors in `domain/model/basket_exchange_view.dart` (`basketExchangeSummaryFor`, `committedDeliveryIdsFor`, `pendingRequestCount`) feed the home `BasketExchangeDashboardCard` and the all-members overview at `/basket-exchange/overview` (CSV export via `saveDatabaseExportFile`). `committedDeliveryIdsFor` mirrors the back's `isBasketCommitted` (offered + both sides of a settled swap, given **or** received) and gates the deliveries offered by both `ProposeBasketExchangeDialog` (new offer) and `SubmitRequestDialog` (counter-delivery). Notification deep links are followed by `NotificationInboxScreen` on tap.
- **Shared baskets (panier partagé)** — `Contract.sharedBaskets: List<SharedBasket{sharedBasketId, memberIds, anchorDeliveryId?}>` overlay (members keep their individual `ContractMember`). Pure selectors in `domain/model/shared_basket_view.dart` (`sharedBasketPickerFor` mirrors the back alternation formula, `contractDeliveriesOrdered`, `pickupDeliveriesFor`, `sharedBasketForMember`, `coSharersFor`). The coordinator authors them on `coordinator_member_contracts_screen.dart` (a "PANIER PARTAGÉ" row + `_SharedBasketDialog` per assigned contract, writing the overlay via `ContractRepository.update` with a `tmp_` `sharedBasketId`). `ContractSyncHandler` needs **no remap** for the nested id — the authoritative `ContractPayload` overwrites the cached contract on the next sync. Members see the alternation read-only on `/contracts` (`_SharedBasketInfo`: "1 distribution sur N" + their pickup dates) and on the planning `DeliveryCard` (planning variant, fed `contracts:` from `member_delivery_plan_screen`; for a plain member the card renders `deliveryWithoutInPreparationContracts` — no IN_PREPARATION contract in the coordinators, products or composition — while actions keep the real delivery; a coordinator registered on a slot reads « inscrit(e) comme coordinateur » since coordinators are never counted; `_sharedBasketLines` shows "c'est votre tour" or "récupéré par {famille}" per linked shared contract). `MutationErrorCode.invalidSharedBasket` mirrors the back. **Exchange interaction**: `memberHoldsBasketOn` (in `shared_basket_view.dart`, mirrors back `Contract.holdsBasketOn`) gates the `BasketExchange` dialogs — `BasketExchangeBloc` now also watches `ContractRepository` (exposed as `state.contracts`), and `ProposeBasketExchangeDialog` / `SubmitRequestDialog` go through `memberMayOfferBasketOn` (subscribed to the contract **and** holding the basket that week): they hide contracts the member is not subscribed to and the weeks where a shared basket is not theirs, and label each delivery with the member's own contracts only (the back enforces the same via `FORBIDDEN`).
- **Password fields** — the show/hide eye is the shared `PasswordVisibilityButton` (`presentation/auth/password_visibility_button.dart`, tooltip « Afficher / Masquer le mot de passe ») on login, activation and reset screens.
- **Password policy** — `domain/auth/password_policy.dart` (`passwordPolicyViolation`, `kPasswordPolicyHint`: ≥ 12 chars, lowercase, uppercase, digit) mirrors the back activation policy (aligned on the Cognito pool) and is applied by the activation, reset-password and forgot-password forms. The activation screen also previews the account being activated (`PublicApi.describeActivation`).
- **Sub-screen navigation** — `ConnectedScaffold(onBack: …)` swaps the navigation-menu button for a back button (forms, wizard steps). `ConnectedScaffold` and `AppShellLayout` both compare the **window** width (`MediaQuery.sizeOf`) to the 1024 px breakpoint — the scaffold body is 281 px narrower than the window when the permanent sidebar is shown. In the desktop layout the content is wrapped in its own `Semantics(container: true)`: the nested navigator's route barrier (`BlockSemantics`) otherwise drops the sidebar, painted before it, from the semantics tree (invisible to screen readers). Owners/producers have no `Member` row: `AuthBloc` takes their menu display name from the cached `Owner` / `ProducerAccount` (the header never falls back to the technical id). Owner request approvals and admin member-join-request approvals go through `confirmApproval` (`presentation/admin/approve_confirmation_dialog.dart`) and confirm success with a snackbar; `/admin/organization-requests?tab=producers` opens on the Producteurs tab. ISO instants are displayed with `formatInstantFr` (`presentation/common/instant_format.dart`).
- **Current menu entry** — the `ShellRoute` passes `state.uri.path` to `AppShellLayout(currentLocation:)` → `NavMenuWidget`, which highlights the entry chosen by `selectedNavRoute` (`presentation/nav/nav_selection.dart`: segment-wise longest route prefix; sub-screens outside their entry's path — delivery tracking / post-delivery / composition, producer deliveries and catalog — are re-attached via `_kParentRoutes`; add new ones there). The tile uses `ListTile(selected:)`, which also exposes the selected state to screen readers.
- **Missing coordinator alert** — « ⚠️ Coordinateur manquant : <contrats> » is the shared `MissingCoordinatorWarning` + `missingCoordinatorContractNames` (`presentation/coordinator/missing_coordinator_warning.dart`), used by the coordinator dashboard cards and the « En cours » / « À venir » cards of `/coordinator/time-slots` (never on « Passées »).
- **Search fields** — every search box (members, contract members, owner users, public AMAP search) filters through `matchesSearch` (`domain/validation/search_text.dart`): letter case and French accents ignored (`normalizeForSearch`, ligatures œ/æ expanded), only fields the user can see (names, email — never technical ids). Reuse it for any new search.
- **Dialog names (a11y)** — every `AlertDialog` passes its title as `semanticLabel`: outside iOS Flutter otherwise names the dialog route with the generic « Alerte ». Icon-only menu buttons (`PopupMenuButton`) carry a `tooltip` naming what they act on; a form field whose visible label sits beside it (e.g. `ContractPriceRow`) gets it through a `Semantics(label:)` wrapper with the visible `Text` excluded (not `MergeSemantics`, which trips a framework semantics assertion around a text field).
- **Unresolved coordinators** — a `DeliveryContract` whose coordinators are not in the local `membersById` (members not synced yet after login) shows « Coordinateur inscrit », never « Coordinateur à confirmer » (reserved for an empty `coordinators` list): `unnamedCoordinatorLabel` (`presentation/coordinator/coordinator_display.dart`). The history « Engagements à venir » card reads « Confirmé - Coordinateur » when the member coordinates the delivery (`deliveryCoordinatorIds`), like the planning. The producer dashboard shows « 🔄 Synchronisation en cours… » while a sync runs with no schedule cached.
- **Read-only badges** — use `StatusBadge` (`presentation/common/status_badge.dart`), never a bare `Chip`, for any chip that only displays a status/role: on the web Flutter exposes every chip as a checkbox (`RawChip` maps `selected` to `aria-checked`); the badge is exposed as plain text.
- **Date fields** — `DatePickerField` keeps its controller in ISO (`yyyy-MM-dd`, what callers read/write) but displays « 1 oct. 2026 »; tapping the field or the calendar button (tooltip « Choisir la {label} ») opens the picker.
- **Notifications** are server-authoritative: `NotificationRepository` only `markRead` / `archive`; inbox at `/notifications` (each card shows « Reçue le … » via `formatInstantFr` and an « Archiver » `IconButton` besides the swipe, for mouse and screen-reader users), reachable for every role from the common menu entry « Notifications » (`nav_items_builder.dart`, above Préférences).
- **Admin alert-copy customisation** — `/preferences` shows an extra "Personnalisation des alertes" card to `UserRole.admin` only (router wires an `AlertTemplatesBloc` alongside `UserPreferencesBloc`; `UserPreferencesScreen(showAlertTemplates: true)`). It edits `Organization.notificationOverrides` (`Map<NotificationCategory, NotificationCopyOverride>`) per `kCustomisableAlertCategories` and saves via `OrganizationRepository.updateNotificationOverrides` (blank entries dropped). `Organization` round-trips the map automatically through `OrganizationPayload`.
- **Organization backup / migration** — `/preferences` shows an admin-only "Sauvegarde & migration" card (`UserPreferencesScreen(backupOrganizationId: <tenant>)`, wired by the router for `UserRole.admin`). Export (all platforms) calls `AdminApi.exportOrganization(orgId)` → saves the raw JSON via `saveDatabaseExportFile` (reused download/save helper). Import is **web-only in V1** (no file-picker dependency on mobile): the button is hidden unless `kIsWeb`, reads a file via `pickJsonFile()` (`data/local/json_file_picker*.dart`, conditional web/stub import), POSTs through `AdminApi.importOrganization` then nudges `SyncBloc` to pull the restored data. When the result carries `warnings` (e.g. members skipped because their email already belongs to an instance owner), they are shown in a dialog instead of the plain success snackbar. The archive stays **opaque** on the client (no Dart model) — it is a pass-through file. Back endpoints: `GET/POST /v1/admin/organizations/{id}/export|import` (see root `AI_CONTEXT.md`).
- **Organization identity config** — `/admin/organization-config` (ADMIN role, nav entry "Configuration de l'organisation") edits `Organization.name`/`contactEmail`/`timezone`/`defaultLanguage`/`website` (`OrganizationConfigScreen`/`OrgConfigBloc`, three cards mirroring `documentation/feature/fr/ui/admin/screen-admin-02-organization-config.md`). Saves via `OrganizationRepository.updateIdentity`, the same full-aggregate `Organization` upsert mechanism as `updateNotificationOverrides`/`updateDefaultDeliveryTemplateId` — no back-end change needed. `/producer-deliveries` (producer role) and `/help` (all roles, nav entry "Aide" between "Préférences" and "Se déconnecter") are also real screens now (previously `PlaceholderScreen`): the former lists the producer's upcoming deliveries (soonest first, every linked AMAP) read-only from its synced `ProducerSchedule` projections (`ProducerScheduleRepository`; a producer never syncs `organization:{id}`); the producer lands on — and « Accueil producteur » opens — `/producer-dashboard` (screen-producer-01-home: « Bonjour {nom} », overview — partner AMAPs, contracts in progress, next delivery —, the 3 next deliveries, active contracts, then quick-access tiles; all computed from the `ProducerSchedule` projections by the pure `producerDashboardSummary` in `domain/model/producer_schedule_view.dart`); the latter is a static screen (guide pointer — a clickable "OUVRIR LE GUIDE" external link when `ServerConfig.guideUrl` is set (from the discovery document's `guide_url` or the preset), informational text otherwise — contact instructions, a 5-entry FAQ accordion, and the installed app version via `PackageInfo`), content sourced from `documentation/guide/fr/aide.md`. The member planning footer's AIDE button navigates to `/help`.
- **Bulk "ask to connect"** — `/members` shows a `_PendingConnectionBanner` when ≥1 `PENDING_ACTIVATION` invitation; its dialog optionally overrides the email subject/body and dispatches `UserManagementEvent.resendAllPendingRequested`, which calls `MemberInvitationRepository.resend(... customEmailSubject/Body)` per pending invite then one sync. `MemberInvitation` carries nullable `customEmailSubject` / `customEmailBody`.
- **Per-delivery basket composition** — informative-only basket contents (see root `AI_CONTEXT.md` invariant). Producer manages the source `ItemType` catalog (`ItemType{id, name, imageSvg?}`, **SVG-only** inline markup) at `/product-types/:id/items` (`ItemTypesScreen`/`ItemTypesBloc`; entry: a "Catalogue de composants" card on `ProductTypeFormScreen`, edit mode). Coordinator composes a delivery at `/coordinator/deliveries/:deliveryId/description` (`DeliveryDescriptionScreen`/`Bloc`; entry: a "Composition du panier" card on the time-slot form `_BasketCompositionBlock`, existing deliveries only — editor loads from the org cache, with the catalogs of **every** producer of the org, synced read-only on the org scope; `ProductTypeSyncHandler` deletes org-scope tombstones by id and `clearScopeData(organization)` drops the org producers' catalogs). When a product has no catalog (e.g. no-account producer), **Ajouter** opens a free-entry form (`_FreeItemDialog`: name required, optional weight, `requiredName`/`kMaxNameLength`) dispatching `freeItemAdded` → a `DeliveryItem` with a local `free-*` id and a name snapshot (no icon). **`DeliveryItem` stays lean** (`itemTypeId` + optional `weight` + tiny `name` snapshot) — the **SVG is never duplicated per item**. On save the bloc stamps `itemsUpdatedAt` on every description whose items changed (the back's stale-copy protection) and **merges** the used components' `ItemType`s (by id) into the flat org-level catalog `Organization.itemTypes` via `OrganizationRepository.updateDeliveryDescription(..., itemTypes:)` in one org `Upsert`; members get the catalog through the `organization` scope. SVG is rendered everywhere via the shared `ItemTypeSvgIcon` (`SvgPicture.string`, `flutter_svg`). Members see it read-only on the planning `DeliveryCard` via `BasketCompositionSection` (collapsible through a private `_CollapsibleSection` whose header is a real `button` + `expanded` semantics node — not `ExpansionTile`, whose header sits under an accessibility-focus-blocked live region that the web engine folds into the card's node; grouped by basket size; the SVG is resolved by `itemTypeId` from `org.itemTypes`, name + optional weight from the item). **The producer composes too**: `ProducerDeliveryCompositionScreen` (route `/producer-deliveries/:organizationId/:deliveryId/composition`, button « COMPOSITION DU PANIER » — `ProducerCompositionButton` — on `/producer-deliveries` active deliveries and on the dashboard's next deliveries) feeds the same editor with a local AMAP view built by `producerCompositionView` (schedule delivery + the producer's `ProductType`s, restricted to the delivery's products and sizes) and injects a `DeliveryCompositionSave` that calls `ProducerScheduleRepository.updateBasketDescriptions` (optimistic schedule write + `ProducerSchedule` upsert on `producer-account:{id}`; icons are resolved server-side, `itemTypes` are not sent).

## Adding a synced entity (recipe)

Mirror a new back `EntityType` in this order (see also the `sync-entity` skill):

1. `domain/sync/entity_type.dart` — enum value + wire-name map entry.
2. `domain/model/<entity>.dart` — Freezed model, snake_case `@JsonKey`s.
3. `domain/sync/entity_payload.dart` — payload variant + `fromJson` switch branch + discriminator `toJson`.
4. `data/local/database/tables.dart` — drift table; CRUD + `clearXForTenant` in the matching `database/*_queries.dart` mixin; wire the clear into `clearScopeData`/`clearAll` and bump `schemaVersion` in `data/local/database.dart` (the version-mismatch strategy rebuilds the cache, no hand-written migration needed).
5. `data/sync/handlers/<entity>_sync_handler.dart` — handler; import + export + registration in `buildEntitySyncHandlers()` (`data/sync/entity_sync_handler.dart`).
6. `data/repositories/<entity>_repository.dart` — mirroring `ProductTypeRepository`.
7. Screens + routes.
8. Tests: wire round-trip, drift CRUD, sync paths, repository writes.
9. `dart run build_runner build --delete-conflicting-outputs`.
