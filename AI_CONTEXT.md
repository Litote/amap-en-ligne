## System overview

Producer-side management app for French AMAP / CSA networks. Offline-first: clients keep a local cache (drift/sqlite) and reconcile with the server through a single sync endpoint.

Monorepo with three independent components:

| Path | Stack | Role |
|------|-------|------|
| `back/` | Kotlin / Gradle multi-module / Ktor / GraalVM Lambda | API server — single authenticated endpoint `POST /v1/sync` |
| `front/` | Flutter / Dart / drift / dio / BLoC | Offline-first mobile + web client |
| `infra/` | Terraform / AWS | DynamoDB, Lambda + API Gateway, Cognito, SNS push |

The root Gradle build orchestrates back and front (`gradlew check`, `acceptanceTest`, `frontTest`, `crossComponentTest`, `frontBuildAndroid`, `frontBuildWeb`, …). **Tool boundary**: Gradle owns the build (`back`/`front`/`convention` composite build); `infra/Makefile` owns deployment orchestration (Terraform + a Docker-wrapped GraalVM cross-compile that calls Gradle + AWS CLI) and is **intentionally not** part of the Gradle composite build. CI bypasses the Makefile and calls `gradlew`/`terraform`/`aws` directly. Agent profiles: `.github/agents/*.agent.md` (Copilot) mirrored in `.claude/agents/*.md` (Claude).

The wire contract between front and back is **the only coupling point** — both sides have parallel domain types kept in sync by hand, pinned by tests on both sides (`front/test/domain/sync_wire_format_test.dart`, back `DataServiceTest` + `JvmDeploymentIntegrationTest`). Documented sync stories live in `acceptance/scenarios/*.json`.

## API surface principle

> **Authenticated actions go through `POST /v1/sync`. Only public bootstrap endpoints live outside sync.**

Public REST endpoints (unauthenticated):

| Route | Purpose |
|-------|---------|
| `GET /.well-known/amap-en-ligne.json` | Instance discovery document |
| `GET /.well-known/apple-app-site-association`, `assetlinks.json` | iOS/Android app links |
| `GET /v1/public/organizations` | Browse visible AMAPs before login — `organization_id`, `name`, `active_status` only: **no contact email** on this world-readable list (back `PublicOrganizationSummary` ↔ front `PublicOrganization`) |
| `GET /v1/public/servers` | List federated peer servers |
| `POST /v1/public/member-join-requests` | Request to join an AMAP |
| `POST /v1/organization-requests` | Request to create an AMAP |
| `POST /v1/producer-requests` | Request to create a producer account |
| `GET /v1/activate?token=` | Read-only preview of an activation token (`kind`, `email`, `organization_name`) so the activation screen can show which account is being activated; same 404/409/410 outcomes as the POST; missing token → `400 INVALID_PAYLOAD` |
| `POST /v1/activate` | Activate an account from an emailed token. The password must satisfy the instance policy (≥ 12 chars, one lowercase, one uppercase, one digit — aligned on the Cognito pool) or the call is rejected `400 WEAK_PASSWORD` before any auth-provider call; mirrored client-side by `front/lib/domain/auth/password_policy.dart` (back `routing/PasswordPolicy.kt`) |

Authenticated REST exceptions (outside sync):

| Route | Purpose |
|-------|---------|
| `GET /v1/admin/producer-accounts/search?q=` | Discovery query for producers not yet visible in the caller's scope feed; returns only active `ACCOUNT_BACKED` producers valid as enrollment/link targets. An account-backed producer's `products` are filled from its `ProductType`s (its real catalog) when `ProducerAccount.products` is empty, so the enrollment step can offer them. ADMIN path is org-scoped; **OWNER path is instance-wide** (no org filter — the OWNER already has full visibility via `instance-owner`), matching name/contact-email case-insensitively. |
| `GET /v1/admin/organizations/{id}/export` | ADMIN (own org) / OWNER (any). Dumps a versioned native-JSON `OrganizationExport` (the `organization:{id}` snapshot + the linked producers' `ProductType` catalogs) for backup / instance migration. |
| `POST /v1/admin/organizations/{id}/import` | ADMIN (own org) / OWNER (any). Restores an `OrganizationExport` into the target org. Trusted restore: written directly through the sync DAOs (bypasses interactive business guards). Ids are preserved; only the source `organizationId` is rewritten to the target; the target org must be **empty** (else `409`). The target keeps its own **name** (the file's name never overwrites it); contact email, timezone and language still come from the file. Imported `Member`s carry PII but no auth identity (`sub` is never on the wire); import auto-creates a `PENDING_ACTIVATION` `MemberInvitation` per emailed member without one, so the admin can (re)invite them (the resend mints the token + email). **Activating such an invitation re-keys the imported row** (`ActivationService.rekeyImportedMember`): the member of the org with the invitation email (case ignored) becomes `memberId = sub` (subscriptions, history, phone kept; roles = the invitation's), every reference follows (`core.withMemberIdReplaced` on the org deliveries, contracts, basket exchanges) and the imported row is deleted — never a duplicate member. **Owner-exclusivity guard**: a member (and its invitation) whose email already belongs to an instance `Owner` is **skipped entirely** (neither the `Member` row nor any invitation is written, case-insensitive) and the collision is reported in `ImportResult.warnings` (French strings the `/preferences` UI shows in a dialog) — importing such a member would collide with the owner's auth identity at activation. See ADR / import-export invariant below. |

Public onboarding submissions (`organization-requests`, `producer-requests`, `public/member-join-requests`) are validated server-side (non-blank names ≤ 200 chars, well-formed email, comment ≤ 2000 chars) → `400 INVALID_PAYLOAD`; a member join request targeting an unknown or inactive organization is `404 NOT_FOUND`, and duplicate pending requests are detected case-insensitively on the email (`409`, field in `error.details.field`); any undecodable request body is `400 INVALID_PAYLOAD` (never 500). Error bodies are RFC 9457 problem details served as `application/problem+json` (every `ErrorResponse`, via the routing `problemDetailsPlugin` installed before `ContentNegotiation`) whose `type` is a `urn:amap-en-ligne:problem:<kind>` URN (machine code in `error.code`). Submitting an organization/producer request also emails the requester an acknowledgement (best-effort, alongside the owner notification).

Auth endpoints (login, refresh, password reset) are served by GoTrue / Cognito directly. Public self sign-up is closed on both providers — Cognito `allow_admin_create_user_only = true` (`infra/modules/cognito`), GoTrue `GOTRUE_DISABLE_SIGNUP=true` (`back/deploy/jvm/docker-compose.yml`, mirrored by the e2e container): accounts are only created through the admin API (the back on activation, Terraform for the initial Cognito owner, `dev-init.sh` / `E2eTestSupport.createUser` with `POST /admin/users` + `email_confirm: true`). Login, refresh and password recovery are unaffected.

## Sync protocol — `POST /v1/sync`

Bearer-authenticated, validated on both sides.

**Request** (`SyncRequest`): `cursors: Map<scopeKey, String?>` + `mutations: List<ClientMutation>` (`Upsert` / `Delete`).
- Scope keys: `producer-account:{id}`, `organization:{id}`, `instance-owner`, plus private notification feeds `member:{sub}` / `owner:{sub}`.
- Missing/null cursor ⇒ bootstrap for that scope; non-null cursor ⇒ full incremental diff strictly after it.

**Response** (`SyncResponse`): `authorized_scopes` + `results: Map<scopeKey, ScopeSyncResult>` + `mutations: List<MutationOutcome>`.
- `authorized_scopes` is authoritative — the client discovers/persists scopes from the server; a disappeared scope means dropping its local cache and scoped pending mutations.
- Each result is `BootstrapScopeResult(items, next_cursor)` or `IncrementalScopeResult(changes, next_cursor)`. The back may answer an incremental request with a bootstrap when the diff is too large.
- `MutationOutcome.serverEntityId` carries the real id allocated for a `tmp_*` upsert; `REJECTED` outcomes carry a `MutationErrorCode`.

**Wire format**:
- snake_case multi-word fields; sealed-class discriminator key `type` with PascalCase values (`"ProductType"`, `"Upsert"`); enum constants uppercase (`"APPLIED"`, `"FORBIDDEN"`).
- `null` nullable fields are **omitted** from JSON (back `explicitNulls = false` ↔ front `include_if_null: false`).

## Cross-component invariants

Preserve these together on both sides:

- **`tmp_` prefix is shared** — front marks optimistic creations with it; back detects it to allocate real ids. Changing it on either side breaks creation flows. Nested ids the back never remaps must not use it: a new `Delivery` (nested in `Organization`) gets a final client-authored `delivery_<unique>` id (`newDeliveryId`); legacy `tmp_delivery_*` ids stay as they are (exchanges and notifications reference them).
- **Cursors are opaque** — clients compare lexicographically, never parse. Cursors attach to scopes, not entity types.
- **`client_op_id` is a server-side idempotency key** — the back persists every APPLIED outcome (`AppliedClientOp`, caller-pinned, 30-day Dynamo TTL) and replays it verbatim when the same `client_op_id` is resent (same `serverEntityId`; a retried `tmp_*` creation never double-creates, and the replay still feeds the in-batch FK remap). The front must keep resending the identical `client_op_id` until it receives an outcome (it already does — `PendingMutations` PK). REJECTED outcomes are not stored: the front drains its queue on any outcome, so they are never retried, and it **restores the server state** of the refused mutation's scope (cursor reset + an immediate second round-trip that bootstraps it — the server never re-sends an unchanged entity, so the optimistic local write would otherwise stay until a full sync) — **except `INTERNAL_ERROR`** (unexpected server-side failure, e.g. persistence outage): the front keeps that mutation queued and resends it on the next sync, offline-like semantics (pinned by `acceptance/scenarios/sync-retry-internal-error-keeps-mutation-queued.json`).
- **Adding a synced entity is a coordinated move** — closed `EntityType` enums + exhaustive switches on both sides. Step-by-step recipes in each component's `AI_CONTEXT.md`.
- **Auth is split per deployment** — `deploy:jvm` → GoTrue (HS256, self-hosted Supabase Auth); `deploy:lambda` → Cognito (RS256 via JWKS). The front implements both providers behind one `AuthService` interface, selected at runtime from a server catalog. **Cognito sends the access token, never the idToken** (back rejects `token_use != "access"`).
- **A producer's account id is NOT its `sub`** — the back resolves it from the `Producer` user row (`producerId == sub` → `producerAccountId`, `AuthorizedScopeResolver`); an account created by an approved `ProducerRequest` gets its own generated id. The front must therefore never use the `sub` as producer tenant: `AuthBloc` resolves `producerAccountId` from the synced `producer-account:{id}` scope (`watchEffectiveProducerAccountId`), and `_requireTenant` prefers it over the sub (a `ProductType` sent with `producer_account_id = sub` is `FORBIDDEN`).
- **Authorization is JWT-only, no revocation (accepted limitation)** — roles come exclusively from the token (`app_metadata.roles` / `cognito:groups`), never cross-checked against persisted `Member.roles`. An already-issued access token keeps its privileges until expiry even after an operator revokes a role, so access-token TTL must stay short (≤ 15 min recommended; the Cognito app client is provisioned with 15-minute access/ID tokens — `infra/modules/cognito`). `email_verified` is **not** enforced at `POST /v1/sync` (the provider already gates role issuance on verification). Enforcement points: `SyncRoute` rejects empty-roles (403) and batches over `MAX_MUTATIONS_PER_SYNC` = 500 (400); `EntityTypeService.requireAnyRole` is the shared role guard; `OrganizationService` is deny-by-default. Details in `back/AI_CONTEXT.md` → Security notes.
- **Producer management modes** — `ProducerAccount.management_mode` (`ACCOUNT_BACKED` / `NO_ACCOUNT`) is authoritative and immutable after creation. `ProducerAccount.products` is the single source of truth; for `NO_ACCOUNT` producers the back derives `Organization.products` automatically. No-account creation uses `tmp_*` ids that the front remaps in `ProducerAccount` + `Organization.producers[]` (not `Organization.products[]`). **Enrolling an account-backed producer** is an `Organization` upsert only: `OrganizationService` (`AccountBackedProducerLinker`) then mirrors every new or status-changed link onto the `ProducerAccount` (`organizations` + its per-org row, `PA#<orgId>` on Dynamo) and fans the account out as a `ProducerAccount` upsert on the org scopes, `instance-owner` and its own feed — otherwise the org never receives its name. Links written before that fix are served by the org-scope bootstrap from `Organization.producers` (`ProducerAccountService.withLegacyLinkedProducers`). The admin's product selection for an account-backed producer (enrollment step 2, « Modifier les produits ») offers its catalog: `ProducerAccount.products` when set, else its `ProductType`s (front `accountBackedCatalog`, same rule as the back producer search).
- **Coordinators** — `DeliveryContract.coordinators: List<Id<Member>>` (the singular `coordinator_id` is gone). The front authors the delivery↔contract links: the delivery form lets the coordinator check active season `Contract`s directly (label = contract name + producer name) and derives one `DeliveryContract` per checked contract (new links start `PENDING` with empty `coordinators`; existing links are preserved as-is while their contract stays checked). The "Produits présents" list is restricted to the products referenced by the checked contracts' `product_prices` (a contract without any price entry falls back to all of its producer's products). A `CONFIRMED` delivery with any contract having empty `coordinators` is rejected with `MISSING_COORDINATOR`; `PLANNED` and post-CONFIRMED states are not checked. **The effective coordinator(s) of a `DeliveryContract` must be chosen among the linked `Contract.coordinators` pool** — the list normally holds a single effective coordinator (present that day) but stays a list for the occasional two-coordinator exception. The back rejects any *newly added* delivery-contract coordinator absent from the contract pool with `INVALID_PAYLOAD` (`OrganizationService.checkCoordinatorsInContractPool`; only new entries are checked, so legacy data and unrelated edits pass through); the front delivery form (`time_slot_form_screen`) restricts the self-assign button and the ADMIN picker to the contract's pool members, and the coordinator dashboard's « ME PORTER COORDINATEUR » only offers the contracts whose pool lists the caller. See ADR-004.
- **Main contract & volunteer staffing** — `Contract.is_main_contract` (bool, default `false`) marks the contract that mobilises volunteers (e.g. vegetables); secondary contracts (eggs, fruit…) need only the coordinator. Authored on the coordinator contract form. **Only main contracts drive the volunteer need**: volunteer slots are materialised on the main contract link only (front `defaultVolunteerSlots`, in weekly generation + delivery form; **no slot is created when no linked contract is main** — the delivery form also hides the "Bénévoles minimum requis" field + slot-time block in that case, lists only main-contract slots in its "Créneaux bénévoles" section, and **prunes legacy empty volunteer slots off non-main contracts on save** — slots with active registrations are kept), and the "N/M bénévoles" counter (`deliveryVolunteerStaffing` / `deliverySlotStatus` / the coordinator tracking present-count) sums only main-contract slots — fallback counts every contract when no linked contract is main (legacy data). The counter also excludes the delivery-wide coordinator union (every linked `DeliveryContract.coordinators`), so a coordinator of one contract registered on another's slot never inflates the count. Purely a front-display + slot-placement concern; the back stores/round-trips the field (Postgres column in `V1__init.sql` — migrations were squashed — Dynamo bool attr) and does **not** change `checkCapacity` (per-slot capacity stays coordinator-excluded per its own contract).
- **Contract lifecycle** — `Contract` carries two new wire fields: `status` (`IN_PREPARATION` | `ACTIVE` | `ENDED`, default `IN_PREPARATION`) and `delivery_template_id` (nullable). **Effectively ended** = `status == ENDED || maxDeliveryDate < today` (back `isEffectivelyEnded`, front `isContractEffectivelyEnded` / `contractStatusView`). Guards: (i) adding new `Contract.members[]` / `Member.contracts[]` entries on an effectively ended contract → `CONTRACT_ENDED`; (ii) linking an effectively ended contract to a new delivery → `CONTRACT_ENDED`; (iii) a non-privileged caller (not OWNER/ADMIN/COORDINATOR) self-subscribing to an `IN_PREPARATION` contract → `FORBIDDEN`. Removals, status edits of existing entries, and edits of already-linked past deliveries stay allowed. The front hides `IN_PREPARATION` contracts from members (visible only to coordinators — `canSeeContractsInPreparation`; on the delivery cards a plain member gets the display-only `deliveryWithoutInPreparationContracts` view, without those links nor the products only they bring), hides deliveries whose linked contracts are all `IN_PREPARATION` from plain members on the planning (coordinators/admins see them flagged "🚧 Contrat inactif" without registration actions — `isDeliveryPendingContractActivation`), and surfaces late rejections via `ContractEndedListener`. Coordinator form: status dropdown (default `IN_PREPARATION`) + optional delivery template dropdown; after creation, a dialog offers to generate weekly deliveries. Back allocates a real id for `tmp_*` contract upserts (like `ProductType`); the batch remap in `DataService` propagates the real id to `OrganizationPayload.deliveries[].contracts[].contractId` in the same sync call. Front-side remap: `ContractSyncHandler.rewriteMutationReference` and `db.remapContractId` also rewrite `Organization.deliveries[].contracts[]` references. Weekly generation is remap-safe: enqueuing the contract upsert triggers a sync right away (`onMutationEnqueued`), so on confirm the front re-reads the org/contracts and re-resolves the saved contract (by id, then natural key — `resolveSavedContract`) before recomputing the plan, and a delivery upsert still queued with the `tmp_*` id is rewritten by the contract remap, so links never carry a dead `tmp_*` id. Linking the contract to an existing delivery also merges its products into that delivery's `basket_descriptions` (existing entries and their items untouched; a legacy delivery without any description stays empty = all products); checking a contract in the delivery form likewise checks its products. Generated deliveries carry `basket_descriptions` derived from the contract's `product_prices` (fallback: the producer's catalog). The delivery form drops a dangling `tmp_*` contract link (no matching cached contract) on save instead of duplicating the re-identified contract.
- **Per-delivery basket composition** — a delivery's informative basket contents live in `Delivery.basket_descriptions: List<BasketDeliveryDescription{product_type_id, basket_size_name, items: List<DeliveryItem>, items_updated_at?}>` inside the `Organization` aggregate (no DAO/migration change). **Two writers**: the coordinator (whole `Organization` upsert) and the account-backed producer, who upserts its `ProducerSchedule` with new `basket_descriptions` for **its own** products (`ProducerScheduleService.applyUpsert`: caller = that producer, link not `TERMINATED`, delivery carries one of its contracts and is neither COMPLETED nor CANCELLED, products ∈ its `Organization.products`, basket size among the product's sizes, same item rules — else `FORBIDDEN`/`INVALID_PAYLOAD`/`NOT_FOUND`); the back replaces the stored descriptions of those (product, size) keys (a description missing from the producer's copy is kept, other producers' untouched), merges the used components' `ItemType`s from the producer's catalog into `Organization.item_types`, and writes the organization + the schedule changes in one transaction. **Last edit wins, stale copies never erase**: the editor stamps every description whose items it changed with `items_updated_at` (ISO instant); `BasketComposition.keepNewestItems` (`service:core`, applied to every `Organization` write and to the producer path) keeps the stored items when the incoming write carries an older or no timestamp (neither side stamped ⇒ incoming wins, legacy), and keeps stored `item_types` entries missing from the incoming write. Adding/removing a description (products present) stays the incoming write's decision. Front: producer entry « COMPOSITION DU PANIER » on `/producer-deliveries` and on the dashboard's next deliveries → `/producer-deliveries/:organizationId/:deliveryId/composition` (`ProducerDeliveryCompositionScreen`: the shared editor fed with a local view built from the schedule + the producer's catalog, restricted to the delivery's products and sizes, saving through `ProducerScheduleRepository.updateBasketDescriptions`); pinned by `ProducerCompositionFlowIntegrationTest` (JVM, real Postgres). A `DeliveryItem` is intentionally **lean**: `item_type_id` (reference) + optional free-text `weight?` + a tiny `name` snapshot (default `""`, for historical accuracy/resilience). **The heavy SVG icon is NOT stored per item** — it lives once in a flat, deduplicated org-level catalog `Organization.item_types: List<ItemType{id, name, image_svg?}>`, resolved by `item_type_id` at display time. This avoids multiplicative duplication: with hundreds of deliveries the SVG would otherwise be copied per item and blow DynamoDB's 400 KB `Organization`-item limit (deliveries are embedded as one JSON attribute — `OrganizationSyncDynamoDAO`). The org-level catalog reaches members because they sync `organization:{id}` but **not** `producer-account:{id}`, where the producer's source `ProductType.item_types` lives. **Producer catalogs on the org scope**: `organization:{id}` also carries, read-only, the `ProductType`s (incl. `item_types`) of every producer linked to the org (link not `TERMINATED`) — `ProductTypeService.snapshot(Organization)` on bootstrap, and each producer `ProductType` upsert/delete fans its `Change` out to those org scopes (`ProductTypeSyncDAO.put/delete(..., fanOutChanges)`, same transaction). Accepted limitation: a producer newly linked to an org only reaches its members' catalogs on their next org bootstrap. `ProductType.item_types` is persisted (Dynamo `item_types` JSON attr, Postgres `product_type.item_types` jsonb — `V2` migration; previously dropped on write, pinned by `acceptance/scenarios/product-type-component-catalog-persisted.json`). **Free entry**: when a product has no catalog (e.g. a `NO_ACCOUNT` producer), the coordinator types the component (`name` required, optional `weight`); it gets a local `free-*` `item_type_id`, no `ItemType` entry and no icon — members read its `name` snapshot. **Images are SVG-only, small and passive** (`image_svg` = inline SVG markup ≤ 10 000 chars, without `<script`, `on*=` event handlers, `javascript:` or `<foreignObject`, rendered via `flutter_svg` `SvgPicture.string`; nulls omitted on the wire) — back `InputRules.optionalSvg` on `ProductType.item_types` and on changed `Organization.item_types` entries (`INVALID_PAYLOAD`) ↔ front `optionalSvgImageError` in the component form: the icons end up in the single `Organization` DynamoDB item (400 KB), where an oversized one used to surface as an endlessly retried `INTERNAL_ERROR`. Flow: producer edits the source catalog at `/product-types/:id/items` (entry on the product-type form); the coordinator composes a delivery at `/coordinator/deliveries/:deliveryId/description` (button on the delivery form, existing deliveries only — editor loads from cache); on save `DeliveryDescriptionBloc` **merges** the used components' `ItemType`s (by id, latest producer definition, existing entries preserved) into `Organization.item_types` in the same org `Upsert`. Members see it read-only on the planning `DeliveryCard` (`BasketCompositionSection`, collapsible, grouped by basket size, SVG resolved from `org.item_types`). Purely informative; the back only checks new/edited components (`OrganizationValidation.basketItemsError`: `name` non-blank ≤ 200, `weight` ≤ 200), mirrored by the editor's free-entry form. **The editor only offers the products present in the delivery** (the product types of its `basket_descriptions`, written by the delivery form for the "Produits présents"; legacy deliveries without any description fall back to every org product); the back rejects (`INVALID_PAYLOAD`) a new component for a product whose producer has no contract linked to the delivery (`OrganizationService.basketCompositionOutsideContractsError`).
- **Delivery closing** — past deliveries are **auto-closed**: `DeliveryAutoCloseService` (`service:organization`) marks every still-active delivery (PLANNED/CONFIRMED/IN_PROGRESS, never CANCELLED) whose day is before today (org timezone) `COMPLETED`, status only (unrecorded registrations untouched), writing the org `Change` + `ProducerScheduleProjection` fan-out like any organization write; run every 15 min alongside the volunteer shortage alerts (JVM poll loop in `bootstrap`, Lambda `VolunteerShortageMainKt` handler — no extra infra). A completed delivery stays pointable (presence / absence / collection after the fact: back accepts it, front tracking keeps the buttons enabled — pinned by `OrganizationServiceTest`, `DeliveryAutoCloseFlowIntegrationTest`, the tracking screen test). A delivery can only be closed (`COMPLETED`) from its scheduled day on (org timezone): back `OrganizationService.checkNoFutureDeliveryCompleted` rejects a delivery newly marked COMPLETED before its day (`INVALID_PAYLOAD`; an already-completed delivery stays editable) ↔ front `isDeliveryClosable` (`domain/validation/delivery_rules.dart`) disables « CLÔTURER LA DISTRIBUTION » (tracking) and « ARCHIVER » (finalisation) before the day, with the date shown. **Day-of records follow the same rule**: before the delivery day, the back rejects (`INVALID_PAYLOAD`, `OrganizationService.checkNoFutureDayOfRecords`) a registration newly set to `CONFIRMED`/`COMPLETED` (present), or to `CANCELLED` (absent) while its slot stays open — cancelling a slot still cascades `CANCELLED` — and a `DeliveryContract` newly `DISTRIBUTED` (collected) ↔ the tracking screen greys « PRÉSENT » / « ABSENT » / « COLLECTÉ » with « Les présences et la collecte pourront être saisies à partir du … ».
- **Presence = CONFIRMED or COMPLETED** — the tracking screen's « PRÉSENT » writes `CONFIRMED` (« ABSENT » writes `CANCELLED`); nothing in the app writes `COMPLETED`, which only comes from imported/legacy data. Both count as a participation everywhere: front `isPresentRegistrationStatus` (`organization_member_view.dart`) drives history, ranking, dashboard « dernière participation » and monthly statistics; the attendance sheets (screen and back `EmailTemplates.attendanceSheets`) list every non-`CANCELLED` registration except the delivery's coordinators. **Contract date bounds are days**: compare a delivery's calendar day (not its date-time) with `Contract.minDeliveryDate`/`maxDeliveryDate` (front `activeContractsForDelivery`), otherwise an evening delivery on the contract's last day is dropped. **A delivery link's display name** is the live `Contract.name` (front `deliveryContractName`), the `DeliveryContract.delivery_description` snapshot being only a fallback (stale after a rename, blank on imported links).
- **Slot lifecycle** — `MemberSlot.slot_id` is nullable, server-allocated (backfilled on first privileged write; never generated by the client). Volunteers can only register on existing slots (`VolunteerMutationValidator` forbids slot creation), so the front materialises default slots on privileged writes: weekly generation and the coordinator delivery form attach an OPEN STANDARD slot (+ EARLY when the template or the delivery override defines one) to the **main contract link** of any slotless delivery (the first link flagged `Contract.is_main_contract`; **no slot is created when no linked contract is main** — see Main contract invariant; `defaultVolunteerSlots` in `front/lib/domain/model/delivery_slots.dart`). **Per-delivery time overrides** — `Delivery` carries optional `standard_end_time` / `volunteer_arrival_time` (`"HH:MM"`) and `early_slot` (reuses `EarlySlot`) overriding the slot times otherwise dictated by the linked `DeliveryTemplate`; resolution is delivery override → template → hard-coded default, applied uniformly by `defaultVolunteerSlots` (front) and `checkCapacity` (back, EARLY-slot cap), so an early slot may be defined directly on a template-less delivery. Nulls are omitted on the wire and the fields ride inside the `Organization` aggregate's `deliveries` JSON (no DAO/migration change). The member planning shows the `COMPLET` state only when slot capacity exists and is exhausted — a slotless delivery offers no registration action. `SlotStatus.CANCELLED` is terminal: privileged cancel cascades registrations server-side and publishes `SLOT_CANCELLED`; reopening is `FORBIDDEN`; deleting a slot with active registrations is `CONFLICT`; reschedule keeps registrations and publishes `SLOT_RESCHEDULED`.
- **Volunteer self-registration** — a VOLUNTEER-only caller may only add/remove their own `registrations` inside `Upsert(OrganizationPayload)`; anything else is `FORBIDDEN` (back `VolunteerMutationValidator`).
- **`BasketExchange` is a reciprocal-swap aggregate** on `organization:{id}` — requests are embedded in `requests`, never a separate entity. The offerer publishes the delivery they want to swap (D1); a requester answers with a **counter-delivery** they offer in return (`BasketExchangeRequest.proposed_delivery_id` / `proposed_contract_id`, nullable on the wire, **required at submission**). The offerer **validates** one request (OPEN→ACCEPTED, atomic PENDING→REJECTED fan-out on the others) or **refuses it individually** (`PENDING→REJECTED`, offer stays OPEN — now supported, offerer-only). For a `tmp_*` request, `serverEntityId` carries the **aggregate root's** id; the front reconciles by diffing `requests` after sync. `Delete` is always `FORBIDDEN` (cancel via `Upsert(status=CANCELLED)`). **Subscription guard**: a member may only offer, or propose in return, the basket of a contract they hold a non-cancelled `ContractMember` subscription to (back `BasketExchangeCommitmentValidator.rejectIfNotBasketHolder` → `FORBIDDEN`, no-op for an unknown contract; front `memberMayOfferBasketOn` filters both dialogs, whose delivery labels only name the member's own contracts). **Basket double-booking guard**: a `(member, delivery)` basket can be committed in at most one active exchange (`isBasketCommitted` back / `committedDeliveryIdsFor` front); violations are `UNIQUE_VIOLATION`. A basket is committed when it is offered (OPEN/ACCEPTED) **or** has changed hands through a settled (ACCEPTED) exchange — both deliveries of an accepted swap (offered D1 + accepted counter D2) are committed for **both** parties (each side gives one basket and **receives** the other), so a basket already exchanged or received cannot be re-offered or re-proposed (enforced on both the offer-creation and request-submission paths, front and back). Notifications carry concrete delivery dates + a `deep_link` (`/basket-exchange/{id}/requests` for the offerer, `/basket-exchange` for requesters). The front surfaces ongoing exchanges on the home dashboard (`BasketExchangeDashboardCard`) and offers coordinators/admins an all-members overview table + CSV export at `/basket-exchange/overview` (plain members are only served open offers and their own exchanges).
- **Producer feed carries the producer's own account** — `producer-account:{id}` serves its `ProducerAccount` (menu name, profile, preferences) alongside its `ProductType`s, notifications and device tokens; `ProducerAccountChangeFactory` also emits every account upsert on that scope.
- **Producer schedules (`ProducerSchedule`, derived projection)** — a producer never receives `organization:{id}` (members' personal data), so its deliveries reach it as one derived `ProducerSchedule` per linked AMAP on `producer-account:{id}` (entity id = `organization_id`): `organization_name` + the deliveries carrying one of **its** contracts (`delivery_id`, `scheduled_date`, `status`, its contracts' `contract_name` / `basket_quantity` / link `status` / `contract_status` (the contract's own lifecycle, so the producer dashboard leaves `IN_PREPARATION` and `ENDED` contracts out of « contrats actifs » and flags them « (en préparation) » on its delivery lines — `producerDashboardSummary`), and the basket compositions of its own products) — never coordinators, slots or registrations. Never stored; `Delete` is `FORBIDDEN` and the **only client write is the producer's basket composition** (see Per-delivery basket composition): `ProducerScheduleService` (`service:producer-account`) serves the bootstrap (organizations whose `producers` list the producer); the writers fan the changes out **atomically** — `OrganizationService` / `ContractService` compute `ProducerScheduleProjection.changes(before, after)` (`service:core`) and pass them to `OrganizationSyncDAO.put` / `ContractSyncDAO.put|delete(..., fanOutChanges)`; an organization write whose `relevantPart` is unchanged (volunteer registrations) skips it without loading contracts. A terminated link (or unlinked producer) yields a `DELETE` tombstone. Accepted limitation: deleting a whole organization leaves its schedules until the producer's next bootstrap. Front: `ProducerScheduleSyncHandler` + drift `producer_schedules` + `ProducerScheduleRepository`, shown on `/producer-deliveries` (upcoming only, soonest first).
- **Admin-only data on the organization scope** — `MemberInvitation` and `MemberJoinRequest` carry the personal data of people who are not members yet: `DataService` serves them on `organization:{id}` only to ADMIN/OWNER callers, at bootstrap **and** in the incremental feed (the `Change` rows are shared by every member of the scope; hidden changes still advance the cursor). The front role guard keeps the matching screens out of reach too.
- **Front role guard (UX)** — `computeRouterRedirect` sends an authenticated user back to their landing page when they open a screen of another role (typed URL, stale link), mirroring the menu: `/owner/*`, `/admin/organization-requests`, `/admin/producer-requests` → OWNER; other `/admin/*`, `/members` → ADMIN; `/coordinator/*`, `/slots`, `/basket-exchange/overview` → COORDINATOR or ADMIN; `/producer-dashboard`, `/producer-deliveries*`, `/product-types*` → PRODUCER; member screens (`/dashboard`, `/contracts`, `/planning`, `/history*`, `/basket-exchange*`) → any AMAP role. The back stays the source of truth for every write.
- **Notifications live on private per-recipient scopes** (`member:{sub}` / `owner:{sub}` / `producer-account:{id}`), keyed by the JWT `sub` — never on `organization:{id}` or `instance-owner`. Server-authoritative: the client only flips `read_at` or archives. Outbound email/push is a best-effort post-commit side-effect; push targets synced `DeviceToken`s on the same feeds (SNS Mobile Push on Lambda, FCM HTTP v1 on JVM; no SMS). See ADR-005.
- **Member notification preferences are honoured server-side** — `MemberPreferences.planning_changes_alerts_enabled` gates `SLOT_CANCELLED` / `SLOT_RESCHEDULED` (`OrganizationService.notifySlotEvent`); `incomplete_slot_reminders_enabled` / `urgent_need_alerts_enabled` gate the **volunteer shortage alerts** (`VOLUNTEER_SHORTAGE` 3 days before, `VOLUNTEER_URGENT_NEED` the day before a delivery still short of volunteers — same staffing rule as the front "N/M bénévoles" counter: main-contract slots, coordinators excluded), sent to the org's active members neither registered on nor coordinating the delivery by the scheduled `VolunteerShortageService` (`service:volunteer-shortage`; every 15 min — JVM in-process loop `VOLUNTEER_SHORTAGE_INTERVAL_MS`, Lambda `deploy.lambda.VolunteerShortageMainKt` on an EventBridge rule), idempotent through `SentAlertDAO` (Postgres `sent_alert` `V4`, Dynamo `pk=SENT_ALERT` + TTL). The former per-slot reminders `reminder_24h/2h/30min_enabled` were **removed** (never implemented); both sides ignore those keys in stored JSON. Outbound channels: `Member.optedNotificationChannels()` (`service:notification-publisher`). See ADR-005 §4.
- **Admin-customisable alert copy** — `Organization.notification_overrides: Map<NotificationCategory, NotificationCopyOverride{title?, body?}>` lets an org ADMIN override the title/body of each org-scoped alert from `/preferences`. Resolution happens at publish sites via `Map.resolveCopy(category, defaultTitle, defaultBody)` (back, `NotificationCopy.kt`): a non-blank override wins per-part, else the hardcoded dynamic default is kept (overrides are applied **verbatim**, no interpolation). Wired in `OrganizationService` (SLOT_*), `BasketExchangeService` (BASKET_EXCHANGE_*), `VolunteerShortageService` (VOLUNTEER_SHORTAGE / VOLUNTEER_URGENT_NEED) and `PublicService` (MEMBER_JOIN_REQUEST_SUBMITTED). **Owner/instance categories** (`ORGANIZATION_REQUEST_SUBMITTED` / `PRODUCER_REQUEST_SUBMITTED`) have no owning org and stay on defaults — out of scope; `DELIVERY_REMINDER` is never published. Only the published org categories are customisable: back `CUSTOMISABLE_ALERT_CATEGORIES` (`OrganizationValidation`, changed entries outside it → `INVALID_PAYLOAD`) ↔ front `kCustomisableAlertCategories`. The front edits them via an admin-only "Personnalisation des alertes" card (`AlertTemplatesBloc`, `kCustomisableAlertCategories`) saving an `Organization` upsert; the map rides inside the `Organization` aggregate (Dynamo JSON attr + Postgres `notification_overrides` jsonb).
- **One pending invitation per email, letter case ignored** — like the member and join-request checks, `Alice@x.fr` and `alice@x.fr` are the same person: `findPendingByEmail` compares without case (Postgres `lower(email)` + unique index on `lower(email)`, migration `V5`; Dynamo lock key `MINV_LOCK#<lowercased email>`), and the `/members` invite form refuses an email with a pending, unexpired invitation (« Une invitation est déjà en attente pour cet email. »). Accepted limitation: a Dynamo lock written before this change under a mixed-case email is not found by the lowercased key.
- **Invitation email copy override** — `MemberInvitation.custom_email_subject` / `custom_email_body` (nullable, omitted when null) let an admin override the invitation email's subject / intro body. `EmailTemplates.memberInvitation` uses them when non-blank but **always appends the activation-link footer + signature** (the link is never droppable). `/members` exposes a bulk "Demander la connexion" action (`UserManagementEvent.resendAllPendingRequested`) that re-sends to every `PENDING_ACTIVATION` invitation, optionally with the overridden copy; the back's resend path (`MemberInvitationService.resendInvitation`) persists and forwards the custom fields.
- **Plain members only get the plain-member view of the organization scope** — a caller without COORDINATOR/ADMIN/OWNER role receives (`core.PlainMemberRedaction`, applied per caller by `DataService` at bootstrap **and** on incremental changes — stored rows and `Change`s stay complete): the other `Member` rows as a public profile (name, roles, status; phone only for COORDINATOR members — called from the delivery cards; no email, subscriptions, registrations, preferences, `registered_at`); in the `Organization`, the others' volunteer registrations without email nor registration date, their cancellations/absences dropped, and on **past** deliveries anonymous (`member_id = "anonymous"`, no name — counters stay right, nobody's attendance history is readable; the link's coordinators keep their identity); no `preparation_notes`; `Contract.members` reduced to the caller's own entry; non-ACTIVE (suspended / deleted) members not served at all and the others' `user_settings` neutralised; producers without contact details (email, address, website), preferences or login users; basket exchanges only when OPEN or when the caller is the offerer or a requester. A payload that is no longer served becomes a `DELETE` tombstone in the incremental feed (e.g. an offer settled between two other members, a member suspended), so the client cache drops it. Instead the served `Organization` carries `participation_counts_by_season` (server-derived, never stored: per season year, one anonymous present-registration count per ACTIVE member) and the front ranking (`memberRankIn` / `participationDistribution` with `seasonYear`) reads it. A plain member's self-registration writes the masked organization back: `OrganizationService` puts the stored values back first (`restoreServedMasks` — only where the incoming part is exactly the served masked form, so a real tampering is still rejected by `VolunteerMutationValidator`) and always drops `participation_counts_by_season`. Coordinators/admins/owners get everything. **The cursor carries the view**: organization-scope cursors issued to a plain member are prefixed `pm.` (`PlainMemberRedaction.CURSOR_MARK`; clients never parse cursors); when the presented cursor's view is not the caller's current one (cache synced before the masking was deployed — whatever the web/back deploy order —, role change either way), `DataService` answers **one** bootstrap in the right view, then plain diffs (the mark is stripped before reading the change log). The front local schema v5 (drops the `organization:*` cursors on upgrade, queue kept) predates this and is kept only because it is released — downgrading the schema would rebuild caches and lose queued mutations. Pinned by `DataServicePlainMemberRedactionTest`, `OrganizationServiceTest`, `PlainMemberRedactionFlowIntegrationTest`, `ModelSerializationTest`, front `organization_member_view_test` / `sync_wire_format_test`.
- **Member PII is synced data** — `Member` carries nullable `first_name`/`last_name`/`email`/`phone` + `account_status` (`ACTIVE`/`SUSPENDED`; invitation states live on `MemberInvitation.status`). `Member.registered_at` (nullable instant, omitted when null) is **server-authoritative**: set at account activation (`ActivationService`) or on creation of a `tmp_*` member, always kept from the stored row on upserts (a client value is ignored); members created before the field existed (Postgres `V3` migration) have none. Shown as « Inscrit le » on the OWNER user detail (earliest across memberships). RGPD delete anonymises the row (PII + sub nulled, `SUSPENDED`) and writes an `AccountDeletionLog`; rows are kept for referential integrity. **Who may delete a `Member`** (`MemberService.applyDelete`): an OWNER (any org) or an ADMIN of the member's own org (another org's member is `NOT_FOUND`), never oneself (`SELF_ACTION_FORBIDDEN`), never the last admin (`LAST_ADMIN`); any other caller is `FORBIDDEN`. A synced member is anonymised + its auth user deleted (best-effort — an imported, never-activated member has none); a never-synced `tmp_*` row is hard-deleted. The `AccountDeletionLog` records `actor_id` (actor's sub) + `actor_role` (`OWNER`/`ADMIN`; Postgres `V6`, legacy Dynamo entries read `actor_owner_id` as an OWNER). Front: OWNER via `/owner/users`, ADMIN via the « Supprimer le membre » action on `/members` (hidden on the caller's own row, last-admin pre-checked).
- **Organization backup / migration** — `OrganizationExport` (`persistence:wire`) is the versioned native-JSON archive of one org: `format_version` + `exported_at` + `source_instance` + `organization_id` + `scopes.{organization, product_types}` (lists of `EntityPayload`, so the wire serializers stay the single source of truth). Export = `organization:{id}` snapshot + linked producers' `ProductType`s (producers = per-org rows ∪ non-terminated `Organization.producers` links, so legacy links are included); import = trusted DAO restore (ProductTypes read from `product_types` **and** the organization section, deduped by id), ids preserved, source `organizationId` rewritten to target, target must be empty. Front round-trips it as a downloaded/uploaded `.json` from an admin-only `/preferences` card.
- **Shared baskets (panier partagé)** — `Contract.shared_baskets: List<SharedBasket{shared_basket_id, member_ids (ordered, ≥2), anchor_delivery_id?}>` is an **overlay** marking that several members alternate on a single physical basket (each keeps their individual `ContractMember` subscription). A coordinator authors them on `/coordinator/member-contracts`. Validation (`ContractService.validateSharedBaskets`, `INVALID_SHARED_BASKET`): ≥2 members, all members are contract members, no member in two baskets of the same contract, all members share an identical subscription. **Alternation is computed client-side, not stored**: order the contract's deliveries by `(scheduledDate, deliveryId)`, `a` = index of `anchor_delivery_id` (0 if null/unknown), `p` = index of the delivery, picker = `member_ids[((p − a) mod n + n) mod n]` — implemented **identically** in `SharedBasketAlternation.kt` (`SharedBasket.pickerFor`) and `front/lib/domain/model/shared_basket_view.dart` (`sharedBasketPickerFor`), pinned by `acceptance/scenarios/contract-shared-basket-*.json`. `shared_basket_id` is a **nested** id: a `tmp_*` one is allocated server-side but **never** echoed via `serverEntityId` (reserved for the contract root) — the front recovers it by overwriting the cached contract from the authoritative `ContractPayload` on the next sync (BasketExchange nested-id convention). **Accepted limitation**: `DeliveryContract.basket_quantity` stays a manual coordinator input — a shared basket counts as one physical basket and nothing auto-derives the count. The member sees the alternation on `/contracts` (1 distribution sur N + their pickup dates) and on each planning `DeliveryCard` (whose turn it is that week). **Interaction with `BasketExchange`**: a shared basket on a given delivery belongs to exactly one family that week, so the exchange flow resolves the *effective holder* via the alternation — `Contract.holdsBasketOn` (back) / `memberHoldsBasketOn` (front), both in the alternation helper. The back rejects (`FORBIDDEN`) an offer or counter-delivery whose `(contract, delivery)` basket is not the caller's that week (`BasketExchangeService.rejectIfNotBasketHolder`); the front hides those weeks/contracts in the propose + submit-request dialogs (fed the org `contracts`). Non-shared contracts are unaffected (holder = always the member).
- **Owner/producer self-edit round-trips `user_preferences`** — `OwnerProfileUpdate` / `ProducerAccountProfileUpdate` (the narrow DTOs backing the `Owner`/`ProducerAccount` self-edit `Upsert` path, deliberately not switched to full-aggregate persistence like `Organization`) now carry `userPreferences`, applied in `updateProfile()`; previously the field was silently dropped despite the mutation reporting `APPLIED`. The front (`OwnerRepository`/`ProducerAccountRepository.updateUserPreferences`) enqueues the upsert on the entity's scope key, mirroring the already-working `Member` path.
- **Input validation on both sides** — every form rule is enforced by the back too (never trust the client) and every back rule a user can hit is pre-checked by the form. Shared primitives: back `service/core/InputRules.kt` (name ≤ 200, email shape, http(s) URL, `HH:MM`, min counts, phone — digits with spaces/dots/dashes/parentheses and an optional leading `+`, 6–30 chars —, basket size names — valid names, unique ignoring case, since a `BasketSize` is identified by its name) ↔ front `domain/validation/input_rules.dart`; entity rules in `*Validation.kt` next to each service (delivery template, contract, product type, organization identity + delivery slot-time overrides, no-account producer, profiles, invitations) ↔ front `domain/validation/{contract,delivery}_rules.dart` + form validators. Rejections are `INVALID_PAYLOAD`. `Organization.timezone` is decoded as a `TimeZone`: an unknown zone makes the whole sync request undecodable (400, the mutation stays queued and blocks the device's syncs), so the front only offers a list (`kSupportedTimezones`); `default_language` is a required two-letter code on both sides. Admin alert overrides must not contain `{…}` placeholders (sent verbatim) — front `alertOverrideError` ↔ back `OrganizationValidation`. On aggregates re-upserted for unrelated reasons (`Organization`, `Member`, `Contract` products), only **changed** fields are checked so legacy data stays editable. **The login email is immutable**: an existing `Member.email` / `Owner.email` may only change by letter case (the auth provider account is never updated from a profile edit) — back `MemberService` / `OwnerService.updateProfile` reject it (`INVALID_PAYLOAD`), the profile dialogs show it read-only. Role label for `VOLUNTEER` is **« Amapien »** everywhere in the UI (« bénévole » only describes the delivery-volunteering activity).
- **Producer pending activation** — `ProducerAccount.pending_activation` (bool, omitted when `false`) is `true` from the OWNER approval of a `ProducerRequest` until the producer activates its account; activation clears it (`ProducerAccountSyncDAO.updatePendingActivation`) and fans the update out on `instance-owner` + every linked `organization:{id}`. The owner user list shows such producers as « Invité » instead of « Actif ». Both request approvals (`OrganizationRequestService` / `ProducerRequestService`) write the created `Organization` / `ProducerAccount` together with an `instance-owner` `Change`, so owners see them on their next incremental sync.
- **Producer suspend/reactivate bans/unbans the linked auth user(s)** — mirroring `Member`/`Owner`, `ProducerAccountService.sideEffects` calls `UserProvisioningPort.banUser`/`unbanUser` for every sub returned by `listAuthSubsByProducerAccount` (no-op for `NO_ACCOUNT` producers, each call isolated in its own `runCatching`). `transition()` rejects an OWNER suspending/reactivating their own producer account with `SELF_ACTION_FORBIDDEN`.
- **Owner user list** — `instance-owner` also carries `MemberInvitation`s (every write fans out there; bootstrap = pending ones), so the OWNER `/owner/users` list shows pending `OwnerInvitation`s and `MemberInvitation`s as « Invité » rows (no account action; skipped when an account already has the email). `NO_ACCOUNT` producers are not users (no login) and are not listed. Rows are built once by `buildInstanceUserRows` (list + detail) and compared by value, so late data (organization names, roles, statuses) refreshes both. An owner `registered_at` at the Unix epoch (the owner seeded by Terraform) is displayed as unknown.
- **Organization identity fans out to `instance-owner`** — an OWNER does not sync `organization:{id}`, so an `Organization` write that changes its identity (name, contact email, active status, website, timezone, default language) also emits an `instance-owner` `Change` (`organizationInstanceOwnerChanges`, `service:core`; wired in `OrganizationService.applyUpsert` and `ImportService`, same transaction through `OrganizationSyncDAO.put(..., fanOutChanges)`). Other edits (deliveries, registrations…) still emit only the `organization:{id}` `Change` and reach an OWNER on the next `instance-owner` bootstrap (the diff-size fallback forces one periodically). Creation fans out too.

## Federated instance discovery

Each instance exposes `GET /.well-known/amap-en-ligne.json` (name, `api_url`, `protocol_version`, `server_version`, optional `server_commit`, `auth.kind` = `gotrue` | `cognito`, optional `terms_url` / `guide_url` — the latter links the help screen's guide card, sourced from `INSTANCE_GUIDE_URL`). `protocol_version` versions the client↔server contract; `server_version` is the deployed application release (`VERSION_NAME` baked at build time into `BuildInfo.VERSION` by a Gradle codegen task in `back/lib/instance-config`, bumped by release-please) — don't conflate the two. `server_commit` is the built commit's short SHA (`GIT_COMMIT_SHA`/`GITHUB_SHA` env at build time, omitted when absent) — it identifies the deployed build exactly since deploys ride every push to main, not just releases. Wrong-server tokens (JWT `iss` mismatch) get `401 WRONG_SERVER` + `token_issuer` so the client can redirect. **Accepted limitation (Lambda)**: `POST /v1/sync` sits behind the API Gateway JWT authorizer (kept on purpose: it also checks the Cognito `client_id`, which the Lambda does not), so a missing/invalid/foreign token gets the gateway's raw `401 {"message":"Unauthorized"}` — never a problem+json nor `WRONG_SERVER` on that route; the front does not handle `WRONG_SERVER` yet.

The front's hardcoded preset list (`front/lib/data/server/server_presets.dart`) is a **temporary bootstrap**, not the target: the goal is instance discovery + cached per-instance config. True federation (inter-server trust, key verification) is not implemented.

### Coverage & CI gating

`.github/workflows/ci.yml` runs three coverage-producing jobs in parallel — `back` (`./gradlew check`, unit only), `front` (`frontTest --coverage` lcov), `acceptance` (`./gradlew allAcceptanceTests`: back acceptance scenarios + cross-component E2E) — and a `sonar` job that `needs:` all three and runs a **scan-only** SonarCloud analysis. SonarCloud coverage is the **union** of the three JaCoCo XML / lcov reports (unit ∪ acceptance ∪ e2e), merged via `-Dsonar.coverage.jacoco.xmlReportPaths` (multiple paths) + `-Dsonar.dart.lcov.reportPaths`. Build mechanics: `jacocoExecReport` (`back/build.gradle.kts`) aggregates whatever `.exec` files a job produced — including `acceptance/e2e/build/jacoco/*.exec` (the e2e back server boots in-JVM) — with no test dependency; the scan-only `sonar` run is gated by `-PsonarExternalCoverage`. **Deploys are gated on the tests**: on a push to `main`, `ci.yml` calls `deploy-lambda.yml` / `deploy-web.yml` (`workflow_call`, secrets passed explicitly) only after `back`, `front` and `acceptance` succeed, picking which deploy from the diff since each target's **last successful deploy** (`changes` job: head commit of the latest `ci.yml` push run whose deploy job succeeded — not `github.event.before`, otherwise a push whose tests failed would have its changes dropped from the next deploy; a manual `workflow_dispatch` deploy is not seen, which only causes an extra redeploy); those workflows no longer trigger on `push` themselves (PR plan + manual dispatch unchanged). **Back `acceptanceTest` is NOT part of `check`** — it runs only via `allAcceptanceTests`; locally, `./gradlew allSonar` still folds in back acceptance (and any present e2e exec).

### E2E gotchas

- **Android**: `E2eTestSupport.ensureAndroidEmulatorRunning()` auto-launches the first AVD (via `flutter emulators`) and skips the test (`assumeTrue`) when none is available.
- **Web build**: `buildFlutterWeb()` builds `--wasm` and patches `flutter_bootstrap.js` to load CanvasKit locally; `flutterServerConfigScript(...)` injects server config into localStorage before app start.
- **Flutter web inputs** use a single off-screen `<input>`; `fill()` does not work. Text fields: click → `waitForSelector` → `Control+A` → `keyboard().insertText(...)`. Password fields: click → `waitForSelector` → `Thread.sleep(500)` → `keyboard().type(...)` (Chrome blocks `insertText` on password inputs; the sleep avoids dropped leading chars).
- **OTP**: always use `ContainerSuite.getRecoveryToken(email)` (6-char numeric OTP). `extractOtpFromEmail()` returns the 56-char magic-link token, which GoTrue's `/verify` rejects with `403 otp_expired`.
